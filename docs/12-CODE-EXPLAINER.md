## 0. ภาพรวม

โปรแกรมเป็น **เว็บแอป** (Next.js + TypeScript) ที่คำนวณ **ในเบราว์เซอร์ทั้งหมด** ไม่มีฐานข้อมูล ไม่มีเซิร์ฟเวอร์คำนวณ

```
ผู้ใช้กรอกฟอร์ม                    ตรวจค่า                     คำนวณ                         แสดงผล
(จำนวนโปรเซส, BT, q,   ──►   validateInput()   ──►   runSimulation()      ──►   ตาราง + Gantt + กราฟเทียบ
 เลือกอัลกอริทึม)              lib/validation.ts       lib/scheduling/simulate.ts      components/*.tsx
                               ผิด → ขึ้นข้อความ E1–E7    ├─ simulateFcfs()  fcfs.ts
                                                       ├─ simulateSjf()   sjf.ts
                                                       ├─ simulateRr()    rr.ts
                                                       └─ finalize()  → TAT, WT, AVG WT
```

**จุดที่ต้องจำ:** ส่วน "คิด" (`lib/`) แยกขาดจากส่วน "หน้าตา" (`components/`) — ไฟล์อัลกอริทึมไม่รู้เลยว่ามีหน้าเว็บ รับตัวเลขเข้า คืนตัวเลขออก จึงทดสอบได้ด้วย unit test ล้วน ๆ

## 1. หลักการทำงานของ 3 อัลกอริทึม

**เงื่อนไขของโจทย์:** ทุกโปรเซสเข้าระบบพร้อมกันที่เวลา 0 (Arrival Time, AT = 0) → ลำดับในคิวเริ่มต้นคือ P1, P2, …, Pn

### 1.1 FCFS — มาก่อนได้ก่อน

- รันตามลำดับ P1 → P2 → P3 จนจบทีละตัว ไม่มีการแย่ง CPU (non-preemptive)
- ข้อเสีย: ถ้าตัวแรกยาวมาก ตัวหลังรอนานหมด (เรียกว่า **convoy effect**)

SET-A: `| P1 0–5 | P2 5–8 | P3 8–16 |` → **AVG WT = 4.33**

### 1.2 SJF (Non-preemptive) — งานสั้นสุดก่อน

- เลือกโปรเซสที่ BT น้อยที่สุดก่อน รันจนจบแล้วค่อยเลือกตัวถัดไป
- ถ้า BT เท่ากัน → เลือกเลขโปรเซสน้อยกว่าก่อน (P1 ก่อน P2)
- ได้เวลารอเฉลี่ยต่ำสุดเสมอเมื่อทุกตัวมาพร้อมกัน

SET-A: `| P2 0–3 | P1 3–8 | P3 8–16 |` → **AVG WT = 3.67** (ต่ำสุดในสามแบบ)

### 1.3 Round Robin (RR) — ผลัดกันทีละ q หน่วย

- คิววนตามลำดับ P1 → P2 → P3 แต่ละตัวได้ CPU **ไม่เกิน q หน่วยต่อรอบ** (Time Quantum)
- ถ้ายังไม่เสร็จ → **กลับไปต่อท้ายคิว** · ถ้าเสร็จ → ออกจากระบบ
- ยุติธรรม ทุกตัวได้ CPU เร็ว แต่เวลารอรวมมักสูงกว่า

SET-A, q = 2:

```
| P1 | P2 | P3 | P1 | P2 | P3 | P1 | P3 | P3 |
0    2    4    6    8    9    11   12   14   16
```

ทีละขั้น (ตรงกับตาราง "วิธีคิดทีละขั้น" ในเว็บ):

| เวลา | ได้ CPU | รัน | เหลือ | ผล | คิวหลังจากนั้น |
|---|---|---|---|---|---|
| 0–2 | P1 | min(2, 5) = 2 | 3 | กลับท้ายคิว | P2 → P3 → P1 |
| 2–4 | P2 | min(2, 3) = 2 | 1 | กลับท้ายคิว | P3 → P1 → P2 |
| 4–6 | P3 | min(2, 8) = 2 | 6 | กลับท้ายคิว | P1 → P2 → P3 |
| 6–8 | P1 | min(2, 3) = 2 | 1 | กลับท้ายคิว | P2 → P3 → P1 |
| 8–9 | P2 | min(2, 1) = 1 | 0 | **เสร็จ CT = 9** | P3 → P1 |
| 9–11 | P3 | min(2, 6) = 2 | 4 | กลับท้ายคิว | P1 → P3 |
| 11–12 | P1 | min(2, 1) = 1 | 0 | **เสร็จ CT = 12** | P3 |
| 12–14 | P3 | min(2, 4) = 2 | 2 | กลับท้ายคิว | P3 |
| 14–16 | P3 | min(2, 2) = 2 | 0 | **เสร็จ CT = 16** | (ว่าง) |

→ **AVG WT = 7.00**

> **พูดในคลิป:** "FCFS ทำงานตามลำดับที่เข้ามา SJF เลือกงานที่สั้นที่สุดก่อน ถ้าเท่ากันเลือกเลขโปรเซสน้อยกว่า ส่วน Round Robin ให้แต่ละโปรเซสใช้ซีพียูได้ไม่เกิน Time Quantum ต่อรอบ ถ้ายังไม่เสร็จก็กลับไปต่อท้ายคิว ทุกอัลกอริทึมในโปรแกรมนี้ถือว่าโปรเซสมาถึงพร้อมกันที่เวลาศูนย์ตามที่โจทย์กำหนด"

#### `lib/scheduling/simulate.ts:53` — ศูนย์กลางการคำนวณ

```ts
export function runSimulation(input: SimulationInput): SimulationResult[] {
  const bt = input.processes.map((p) => p.burstTime);
  for (const algorithm of ["FCFS", "SJF", "RR"]) {
    if (!input.algorithms.includes(algorithm)) continue;   // ข้ามตัวที่ไม่ได้เลือก
    case "FCFS": results.push(finalize("FCFS", bt, simulateFcfs(bt)));
    case "SJF":  results.push(finalize("SJF",  bt, simulateSjf(bt)));
    case "RR":   results.push(finalize("RR",   bt, simulateRr(bt, input.timeQuantum), ...));
  }
}
```

ทุกอัลกอริทึมได้ `bt` **ชุดเดียวกัน** — นี่คือเหตุผลที่เปรียบเทียบกันได้อย่างยุติธรรม

#### `lib/scheduling/fcfs.ts:9–15` — FCFS

```ts
let t = 0;                                   // นาฬิกาเริ่มที่ 0
for (let i = 0; i < burstTimes.length; i++) {// วน P1, P2, P3 ตามลำดับ
  startTime[i] = t;                          // ST = เวลาตอนนี้
  completionTime[i] = t + burstTimes[i];     // CT = เริ่ม + BT
  gantt.push({ processId: i + 1, start: t, end: completionTime[i] });
  t = completionTime[i];                     // เลื่อนนาฬิกาไปตอนจบ

```

#### `lib/scheduling/sjf.ts:6–8` — SJF (ต่างจาก FCFS แค่ "เรียงก่อน")

```ts
const order = burstTimes
  .map((bt, i) => ({ bt, i }))
  .sort((a, b) => a.bt - b.bt || a.i - b.i);  // BT น้อยก่อน; เท่ากัน → เลขโปรเซสน้อยก่อน
```

จากนั้นบรรทัด 14–20 วนแบบเดียวกับ FCFS แต่วนตาม `order`
**ทำไมเรียงครั้งเดียวพอ:** ทุกตัวมาถึงเวลา 0 ไม่มีใครมาเพิ่มระหว่างทาง (คอมเมนต์บรรทัด 5)

#### `lib/scheduling/rr.ts:9–24` — Round Robin (หัวใจของโปรแกรม)

```ts
const remaining = [...burstTimes];             // เวลาที่ยังเหลือของแต่ละตัว
const queue = burstTimes.map((_, i) => i);     // คิวเริ่ม: P1, P2, P3

let t = 0;
while (queue.length > 0) {                     // วนจนคิวว่าง
  const i = queue.shift();                     // หยิบหัวคิว
  const runTime = Math.min(quantum, remaining[i]); // รันได้ไม่เกิน q (ถ้าเหลือน้อยกว่า q ก็รันเท่าที่เหลือ)

  if (startTime[i] === -1) startTime[i] = t;   // ST = ครั้งแรกที่ได้ CPU เท่านั้น
  gantt.push({ processId: i + 1, start: t, end: t + runTime });
  t += runTime;
  remaining[i] -= runTime;

  if (remaining[i] === 0) completionTime[i] = t; // เสร็จ → บันทึก CT
  else queue.push(i);                            // ยังไม่เสร็จ → ต่อท้ายคิว
}
```

จุดที่ควรชี้ในคลิป:
- **บรรทัด 15** `Math.min(quantum, remaining[i])` — ใช้ q เต็ม หรือเท่าที่เหลือ
- **บรรทัด 17** ST เก็บแค่ครั้งแรก (ตั้งค่าเริ่ม −1 ไว้ที่บรรทัด 5)
- **บรรทัด 23** `queue.push(i)` — "กลับไปต่อท้ายคิว"

> **พูดในคลิป:** "เมื่อกดคำนวณ ฟังก์ชัน calculate จะตรวจค่าก่อน ถ้าถูกต้องจะส่ง Burst Time ไปให้ runSimulation ซึ่งเรียกอัลกอริทึมที่ผู้ใช้เลือกด้วยข้อมูลชุดเดียวกัน FCFS วนตามลำดับ SJF เรียงตาม Burst Time ก่อนแล้ววนแบบเดียวกัน ส่วน Round Robin ใช้คิว หยิบหัวคิวมารันไม่เกิน Quantum ถ้ายังเหลือเวลาก็ push กลับท้ายคิว วนจนคิวว่าง"

### 3.2 การตรวจค่าผิด — `lib/validation.ts:37`

ตรวจทุกครั้งก่อนคำนวณ ถ้าผิดจะ **ไม่คำนวณ** และขึ้นข้อความภาษาไทยใต้ช่องที่ผิด + กล่องรวมด้านบน

## 4. การคำนวณและแสดง ST / CT / TAT / WT / AVG WT

### 4.1 สูตร (ทำที่จุดเดียว) — `lib/scheduling/simulate.ts:18` `finalize()`

```ts
const processes = burstTimes.map((bt, i) => {
  const turnaroundTime = output.completionTime[i];   // TAT = CT − AT และ AT = 0 → TAT = CT
  return {
    id: i + 1,
    burstTime: bt,
    startTime: output.startTime[i],                  // ST จากอัลกอริทึม
    completionTime: output.completionTime[i],        // CT จากอัลกอริทึม
    turnaroundTime,
    waitingTime: turnaroundTime - bt,                // WT = TAT − BT
  };
});
const sumWt = processes.reduce((acc, p) => acc + p.waitingTime, 0);
avgWaitingTime: round2(sumWt / n),                   // AVG WT = ΣWT ÷ n ปัด 2 ตำแหน่ง
```

| ค่า | ความหมาย | มาจากไหน |
|---|---|---|
| **ST** Start Time | เวลาที่ได้ CPU **ครั้งแรก** | อัลกอริทึมแต่ละตัวบันทึก (RR: `rr.ts:17`) |
| **CT** Completion Time | เวลาที่ทำงานเสร็จ | อัลกอริทึมบันทึกตอนเหลือ 0 |
| **TAT** Turnaround Time | CT − AT = CT (เพราะ AT = 0) | `simulate.ts:25` |
| **WT** Waiting Time | TAT − BT = เวลาที่นั่งรอในคิว | `simulate.ts:32` |
| **AVG WT** | ผลรวม WT ÷ จำนวนโปรเซส | `simulate.ts:44` + `round2` บรรทัด 13 |

**ทำไมสูตรอยู่ที่ `finalize` ไม่ใช่ในแต่ละอัลกอริทึม:** เขียนสูตรครั้งเดียว ใช้ร่วมทั้ง 3 ตัว → ไม่มีทางที่ FCFS คิด WT แบบหนึ่ง RR คิดอีกแบบ

**ทำไมปัดด้วย `round2`:** ค่าที่โชว์บนจอกับค่าที่ unit test ตรวจเป็นตัวเดียวกัน (11 ÷ 3 = 3.666… → 3.67)

## 6. เปรียบเทียบผลเมื่อ Burst Time หรือ Quantum เปลี่ยน

### 6.1 ส่วนที่ใช้โชว์บนจอ

| ส่วน | ไฟล์ | ทำอะไร |
|---|---|---|

| กราฟ "Time Quantum มีผลอย่างไร" | `components/QuantumSweep.tsx:29` ใช้ `quantumSweep()` ใน `lib/scheduling/trace.ts:129` | คำนวณ RR **ด้วยโค้ดจริง** ทุกค่า q ตั้งแต่ 1 ถึง BT สูงสุด (หรือถึง q ปัจจุบันถ้ามากกว่า, ไม่เกิน 100 — `QuantumSweep.tsx:43`) แล้ววาดเป็นกราฟ · **คลิกจุดไหน = คำนวณใหม่ด้วย q นั้นทันที** (`app/page.tsx:155`) |

### 6.2 ตัวเลขจริง — SET-A เปลี่ยน Quantum

| q | 1 | **2** | 3 | 4 | 5 ขึ้นไป |
|---|---|---|---|---|---|
| AVG WT ของ RR | 6.67 | **7.00** | 5.67 | 6.33 | 4.33 (= FCFS) |

ประเด็นที่ควรพูด:
- **q เล็ก** → สลับบ่อย ทุกตัวต้องรอกันหลายรอบ WT สูง
- **q ใหญ่ ≥ BT ของทุกตัวที่ยังต้องผลัด** → ทุกตัวรันจบในรอบเดียว **RR กลายเป็น FCFS** (ที่ q ≥ 5 ได้ 4.33 เท่า FCFS)
- **ไม่ได้ลดลงเรื่อย ๆ** — q = 2 แย่ที่สุด, q = 3 ดีกว่า q = 4 → ขึ้นกับว่า q "ตัด" งานแต่ละตัวตรงไหน กราฟในเว็บเห็นชัด

### 6.3 ตัวเลขจริง — เปลี่ยน Burst Time (q = 2)

| ชุดข้อมูล | FCFS | SJF | RR | สังเกต |
|---|---|---|---|---|
| SET-A: 5, 3, 8 | 4.33 | **3.67** | 7.00 | ค่าตั้งต้น |
| P1 ยาวขึ้น: **10**, 3, 8 | 7.67 | **4.67** | 9.33 | งานยาวอยู่หน้า → FCFS แย่ลงมาก (convoy effect) SJF ยังดีสุดเพราะย้ายงานยาวไปท้าย |
| P3 สั้นลง: 5, 3, **1** | 4.33 | **1.67** | 4.33 | งานสั้นอยู่ท้าย → FCFS ไม่ได้ประโยชน์ แต่ SJF ดึงขึ้นมาก่อน WT ลดฮวบ |

สรุปที่ใช้ปิดคลิปได้: **SJF ได้ AVG WT ต่ำสุดเสมอเมื่อทุกโปรเซสมาพร้อมกัน**, FCFS ขึ้นกับลำดับที่เข้ามา, RR ขึ้นกับการเลือก q (แลกเวลารอกับความยุติธรรม/การตอบสนอง)

> **พูดในคลิป:** "เมื่อใช้ข้อมูลชุดเดียวกัน SJF ได้เวลารอเฉลี่ยต่ำสุด ถ้าเปลี่ยน P1 ให้ยาวเป็น 10 FCFS แย่ลงจาก 4.33 เป็น 7.67 เพราะทุกตัวต้องรองานยาวที่อยู่หน้าสุด ส่วน Quantum ของ Round Robin กราฟนี้คำนวณทุกค่า q ด้วยโค้ดจริง จะเห็นว่า q เล็กทำให้รอนาน และเมื่อ q ใหญ่พอ Round Robin จะทำงานเหมือน FCFS คลิกจุดบนกราฟเพื่อคำนวณใหม่ด้วย q นั้นได้ทันที"

ตอบ: เลขโปรเซสน้อยกว่าก่อน — `sjf.ts:8` `a.bt - b.bt || a.i - b.i` (ถ้าผลต่าง BT เป็น 0 จะไปเทียบเลขโปรเซสแทน)

**ถาม: ทำไม TAT = CT?**
ตอบ: TAT = CT − AT และโจทย์กำหนด AT = 0 ทุกโปรเซส (`simulate.ts:25`)

**ถาม: เศษสุดท้ายของ RR ที่น้อยกว่า q ทำยังไง?**
ตอบ: รันเท่าที่เหลือ ไม่ปัดขึ้นเป็น q — `Math.min(quantum, remaining[i])` (`rr.ts:15`) เช่น P2 เหลือ 1 ที่เวลา 8 รันแค่ 8–9

**ถาม: ป้องกันค่าผิดอย่างไร?**
ตอบ: `validateInput` ตรวจก่อนคำนวณทุกครั้ง กฎ E1–E7 ทุกค่าต้องเป็นจำนวนเต็มบวก จำนวนโปรเซสไม่เกิน 10 ถ้าผิดจะไม่คำนวณเลย

**ถาม: รู้ได้ยังไงว่าโปรแกรมคำนวณถูก?**
ตอบ: (1) เทียบชุด SET-A กับการคำนวณมือ (`docs/07-HAND-CALCULATION.md`) ตรงทุกช่อง (2) unit test 60 ข้อ ตรวจทั้งค่าคำนวณมือและกฎทั่วไป เช่น WT = TAT − BT และเวลารวมใน Gantt = ผลรวม BT (3) test รันทุกครั้งที่ build ถ้าผิด deploy ไม่ได้

**ถาม: ทำไม SJF ได้ AVG WT ต่ำสุด?**
ตอบ: งานสั้นทำก่อน → งานที่เหลือรอสั้นลง ตัวที่รอนานคือตัวยาวที่อยู่ท้ายซึ่งมีจำนวนน้อย

**ถาม: Quantum เท่าไรดีที่สุด?**
ตอบ: ไม่มีค่าตายตัว ขึ้นกับชุด BT — ดูกราฟ Quantum ในเว็บ ชุด SET-A q ≥ 5 ได้ AVG WT ต่ำสุด (เท่า FCFS) แต่ q ใหญ่เกินไปก็เสียข้อดีของ RR เรื่องการตอบสนองที่เร็ว

**ถาม: ใช้ AI ช่วยตรงไหน?** — ดูตาราง "Use of AI" ใน `README.md` (ใช้สำหรับวิดีโอส่วนที่ 3)

## 9. ศัพท์ที่ต้องรู้

| ศัพท์ | ความหมายแบบง่าย |
|---|---|
| Process (P1, P2, …) | งานที่ต้องใช้ CPU |
| AT — Arrival Time | เวลาที่งานมาถึง (โปรแกรมนี้ = 0 ทุกตัว) |
| BT — Burst Time | เวลาที่งานต้องใช้ CPU ทั้งหมด |
| ST — Start Time | เวลาที่ได้ CPU ครั้งแรก |
| CT — Completion Time | เวลาที่งานเสร็จ |
| TAT — Turnaround Time | ตั้งแต่มาถึงจนเสร็จ = CT − AT |
| WT — Waiting Time | เวลาที่นั่งรอ (ไม่ได้ใช้ CPU) = TAT − BT |
| AVG WT | WT เฉลี่ยของทุกงาน — ยิ่งน้อยยิ่งดี ใช้เทียบอัลกอริทึม |
| Time Quantum (q) | เวลาสูงสุดต่อรอบใน Round Robin |
| Ready Queue | คิวของงานที่พร้อมรัน รอ CPU ว่าง |
| Non-preemptive | ได้ CPU แล้วรันจนจบ ไม่ถูกแย่งกลางคัน (FCFS, SJF) |
| Preemptive | ถูกพักกลางคันได้ (RR พักเมื่อครบ q) |
| Gantt chart | แถบแสดงว่าช่วงเวลาไหนใครได้ CPU |
| Convoy effect | งานยาวอยู่หน้า ทำให้งานสั้นข้างหลังรอนานกันหมด |
| Unit test | โปรแกรมเล็ก ๆ ที่ตรวจว่าฟังก์ชันคืนค่าถูกต้องอัตโนมัติ |
